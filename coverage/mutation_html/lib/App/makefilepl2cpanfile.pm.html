  247: =head1 DESCRIPTION
  248: 
  249: A Perl distribution lists the modules it needs in its F<Makefile.PL>.
  250: Many tools (for example C<cpanm --installdeps .> and CI systems) prefer
  251: a F<cpanfile> instead.  This module reads a F<Makefile.PL> and writes the
  252: same list in F<cpanfile> form, so you only keep the list in one place.
  253: 
  254: The F<Makefile.PL> is B<never run>.  It is read as plain text and
  255: searched for the parts that list dependencies.  This makes the tool safe
  256: to use on code you do not trust, but it also means that it cannot see
  257: dependencies that are computed while the program runs (see
  258: L</COMMON PITFALLS>).
  259: 
  260: =head2 What it reads
  261: 
  262: =over 4
  263: 
  264: =item * C<PREREQ_PM>, C<BUILD_REQUIRES>, C<TEST_REQUIRES> and
  265: C<CONFIGURE_REQUIRES>.  These become C<requires> lines in the C<runtime>,
  266: C<build>, C<test> and C<configure> phases.
  267: 
  268: =item * C<prereqs =E<gt> { PHASE =E<gt> { RELATIONSHIP =E<gt> { ... } } }>
  269: blocks (the CPAN::Meta::Spec version 2 layout), wherever they appear -
  270: also inside C<META_MERGE>.
  271: 
  272: =item * The older version 1 layout, directly inside C<META_MERGE>:
  273: C<requires>, C<recommends>, C<suggests> and C<conflicts> become lines of
  274: that kind in the C<runtime> phase; C<build_requires> and
  275: C<configure_requires> become C<requires> lines in the C<build> and
  276: C<configure> phases.
  277: 
  278: =item * C<MIN_PERL_VERSION>, which becomes C<requires 'perl', 'VERSION';>.
  279: 
  280: =item * A C<#> comment after an entry.  It is copied to the F<cpanfile>.
  281: 
  282: =back

  284: =head2 What it writes
  285: 
  286: 	# Generated from Makefile.PL using makefilepl2cpanfile
  287: 
  288: 	requires 'perl', '5.010';

  290: 	requires 'Moo', '2.000';   # object system
  291: 	requires 'Try::Tiny';

  298: 	on 'develop' => sub {
  299: 		requires 'Perl::Critic';

  302: Runtime dependencies come first, without an C<on> block.  The other
  303: phases follow in this order: C<configure>, C<build>, C<test>, C<develop>.
  304: Inside each phase, C<requires> lines come first, then C<recommends>, then
  305: C<suggests>, and the modules are in alphabetical order.  The same input
  306: always gives exactly the same output.

  308: =head1 CONFIGURATION
  309: 
  310: When C<with_develop> is true (the default), some developer tools are
  311: added to the C<develop> phase.  By default these are L<Devel::Cover>,
  312: L<Perl::Critic>, L<Test::Pod> and L<Test::Pod::Coverage>.
  313: 
  314: To choose your own list, create the file
  315: F<~/.config/makefilepl2cpanfile.yml>:
  316: 
  317: 	develop:
  318: 	  Perl::Critic: 0
  319: 	  Devel::Cover: 0
  320: 	  My::Extra::Tool: '1.00'

  323: version".  Your list B<replaces> the default list; it is not added to it.
  324: Names that are not valid module names, and versions that are not version
  325: numbers, are ignored with a warning, so a mistake in this file can never
  326: put unexpected code into your F<cpanfile>.

  328: =head1 DATA STRUCTURE
  329: 
  330: C<parse_prereqs()> returns a hash reference with three levels:
  331: 
  332: 	{
  333: 		PHASE => {
  334: 			RELATIONSHIP => {
  335: 				'Module::Name' => { version => '1.0', comment => 'why it is needed' },
  336: 			},
  337: 		},
  338: 	}
  339: 
  340: =over 4
  341: 
  342: =item * PHASE is one of C<runtime>, C<configure>, C<build>, C<test> or
  343: C<develop>.
  344: 
  345: =item * RELATIONSHIP is one of C<requires>, C<recommends>, C<suggests> or
  346: C<conflicts>.
  347: 
  348: =item * C<version> is the version requirement exactly as it was written:
  349: a single version (C<'1.60'> stays C<'1.60'>) or a version range such as
  350: C<'E<gt>= 1.2, E<lt> 2.0'>.  It is C<0> when there is no requirement.
  351: 
  352: =item * C<comment> is the text of the C<#> comment after the entry, or
  353: C<undef> when there is none.
  354: 
  355: =back
  356: 
  357: A phase or relationship with no modules is not present at all.

  359: =head1 ENCODING
  360: 
  361: =over 4
  362: 
  363: =item * B<The Makefile.PL file> is read as UTF-8.  Comments may contain
  364: any printable Unicode text, including accented letters, emoji and
  365: combining marks; they are copied to the output unchanged.  Control
  366: characters (other than TAB) and Unicode direction-override characters
  367: are removed from comments, so that the generated file cannot be made to
  368: look different from what it really contains.  If the file is not valid UTF-8 you get a
  369: warning and processing continues (see L</generate(%args)>).
  370: 
  371: =item * B<The returned cpanfile text> is a Perl character string.  Write
  372: it with a UTF-8 output layer, for example C<path(...)-E<gt>spew_utf8> or
  373: C<binmode $fh, ':encoding(UTF-8)'>.  Otherwise Perl warns
  374: "Wide character in print" when a comment contains non-ASCII text.
  375: 
  376: =item * B<The existing argument> and B<the content argument of
  377: parse_prereqs()> must be character strings: decode them first (for
  378: example with C<slurp_utf8>).  Raw bytes work for plain ASCII, but a
  379: non-ASCII comment would come back as separate bytes.
  380: 
  381: =item * B<Module names> must be plain ASCII (A-Z, a-z, 0-9, C<_> and
  382: C<::>), as CPAN requires.  A name with any other character is ignored.
  383: This also stops look-alike names, such as C<Test::More> written with a
  384: Cyrillic letter.
  385: 
  386: =item * B<Version numbers> may use only the ASCII digits 0-9, C<.>,
  387: C<_> and a leading C<v>, and must contain at least one digit.  A version
  388: range joins such numbers, each after one of the operators C<E<gt>=>,
  389: C<E<lt>=>, C<==>, C<!=>, C<E<gt>> or C<E<lt>>, with commas.  The whole
  390: value is checked: C<'1.0-TRIAL'> is not shortened to C<'1.0'>.  Anything
  391: else is treated as "no minimum version".
  392: 
  393: =item * B<The YAML configuration file> is read as UTF-8; the same rules
  394: for names and versions apply.
  395: 
  396: =item * B<File names> are passed to the operating system unchanged.
  397: Names with spaces, non-ASCII letters or shell characters such as C<;>
  398: and C<|> are safe: no shell is ever used.

  404: =head2 generate(%args)
  405: 
  406: =head3 PURPOSE
  407: 
  408: Reads a F<Makefile.PL> and returns the text of a matching F<cpanfile>.
  409: The F<Makefile.PL> is read as text and is never run.
  410: 
  411: =head3 ARGUMENTS
  412: 
  413: Give the arguments as a list of name/value pairs, or as one hash
  414: reference.  All of them are optional.
  415: 
  416: =over 4
  417: 
  418: =item * C<content> - the text of a F<Makefile.PL>, for example from
  419: L</read_makefile($path)>.  When it is given it is used as it is, and
  420: C<makefile> is ignored and nothing is read.  Use it to read the file once
  421: and use the same text for more than one purpose.
  422: 
  423: =item * C<makefile> - the path of the F<Makefile.PL> to read.  Default:
  424: C<'Makefile.PL'> in the current directory.  Anything that turns into a
  425: path when used as a string is accepted, such as a L<Path::Tiny> object.
  426: A filehandle or another kind of reference is refused with
  427: C<Cannot read>.
  428: 
  429: =item * C<existing> - the text of your current F<cpanfile>.  Default:
  430: C<''> (none).  Only its C<on 'develop' =E<gt> sub { ... }> section is
  431: used.  Every C<requires>, C<recommends>, C<suggests> and C<conflicts>
  432: line in that section is copied to the new text, so your hand-written developer
  433: dependencies are kept.  Lines that are commented out are not copied.
  434: An entry whose name is not a valid module name is dropped.  An entry
  435: whose version is not a version number or version range is kept without a
  436: version, and you get a warning.
  437: 
  438: =item * C<with_develop> - true or false.  Default: true.  When true, the
  439: developer tools from the configuration file (see L</CONFIGURATION>), or
  440: the default tools, are added to the C<develop> phase as C<requires>.  A
  441: tool that is already in the develop phase, from the F<Makefile.PL> or
  442: from C<existing>, is left exactly as it is.
  443: 
  444: =back
  445: 
  446: =head3 RETURNS
  447: 
  448: A string: the complete F<cpanfile>.  It always starts with the line
  449: C<# Generated from Makefile.PL using makefilepl2cpanfile> and always ends
  450: with exactly one newline.  The layout is described in
  451: L</What it writes>.  A F<Makefile.PL> with no dependencies gives just
  452: the first line.
  453:

  455: 
  456: =over 4
  457: 
  458: =item * Reads the C<makefile> file.
  459: 
  460: =item * When C<with_develop> is true, reads
  461: F<~/.config/makefilepl2cpanfile.yml> if it exists.
  462: 
  463: =item * Never writes, creates or deletes any file.
  464: 
  465: =item * May print warnings (see MESSAGES below).
  466: 
  467: =item * Does not change the caller's C<$@>, C<$!> or C<$_>.
  468: 
  469: =back

  484: =head3 HOW IT WORKS
  485: 
  486: =over 4
  487: 
  488: =item 1. Check that C<makefile> is a readable, regular file.
  489: 
  490: =item 2. Read it as UTF-8.  If that fails because of bad UTF-8, warn and
  491: read the raw bytes instead.  Any other read error is passed on.
  492: 
  493: =item 3. Find C<MIN_PERL_VERSION> and call L</parse_prereqs($content)>.
  494: 
  495: =item 4. Copy the develop entries from C<existing>, without replacing
  496: entries that came from the F<Makefile.PL>.
  497: 
  498: =item 5. If C<with_develop> is true, add each configured tool that is
  499: not already in the develop phase.
  500: 
  501: =item 6. Format and return the text.
  502: 
  503: =back

 1460: =head1 COMMON PITFALLS
 1461: 
 1462: =over 4
 1463: 
 1464: =item * B<Code in Makefile.PL is not run.>  Dependencies that are built
 1465: by code are not seen, for example C<PREREQ_PM =E<gt> \%deps> or a list
 1466: returned by a function.  Entries inside a condition, such as
 1467: C<$^O eq 'MSWin32' ? ('Win32' =E<gt> 0) : ()>, are seen but become
 1468: unconditional.  Write such dependencies as plain entries, or add them to
 1469: the F<cpanfile> another way.
 1470: 
 1471: =item * B<Only the develop section of an existing cpanfile is kept.>
 1472: Hand edits anywhere else (for example a C<feature> block or an extra
 1473: C<on 'test'> line) are lost when you regenerate.  Put hand-written
 1474: entries in C<on 'develop' =E<gt> sub { ... }>.
 1475: 
 1476: =item * B<Conditions inside the kept develop section are removed.>  An
 1477: C<if (...) { requires 'X' }> inside the develop block is carried over as
 1478: a plain C<requires 'X'>.  Comments in the develop block are not kept.
 1479: 
 1480: =item * B<Which entry wins.>  When the same module is listed twice in the
 1481: same phase and relationship, the first one wins.  The simple keys
 1482: (C<PREREQ_PM> and friends) are read before C<prereqs> blocks, and entries
 1483: from F<Makefile.PL> win over entries in the existing develop section.
 1484: The same module under two different relationships (for example
 1485: C<requires> and C<recommends>) is kept twice.
 1486: 
 1487: =item * B<The configuration file replaces the default tools.>  If you
 1488: list only C<My::Tool>, then C<Perl::Critic> and the others are no longer
 1489: added.  List them too if you want them.
 1490: 
 1491: =item * B<undef means "use the default".>  C<makefile =E<gt> undef> reads
 1492: F<Makefile.PL>; C<existing =E<gt> undef> is the same as C<''>; and
 1493: C<with_develop =E<gt> undef> means B<true>.  Use C<with_develop =E<gt> 0>
 1494: to turn developer tools off.
 1495: 
 1496: =item * B<parse_prereqs(undef) is silent.>  It returns an empty hash
 1497: reference with no warning, so a failed file read can look like "no
 1498: dependencies".  Check that the read worked before you call it.
 1499: 
 1500: =item * B<The output depends on who runs it.>  With C<with_develop> on,
 1501: the tool list comes from the home directory of the current user.  Use
 1502: C<with_develop =E<gt> 0> when every computer must produce the same file.
 1503: 
 1504: =item * B<generate() does not write any file.>  It returns the text.
 1505: Save it yourself (see L</SYNOPSIS>) or use the command-line tool.
 1506: 
 1507: =item * B<Relative paths> in C<makefile> are relative to the current
 1508: working directory, not to your script.
 1509: 
 1510: =item * B<Warnings are not errors.>  Problems such as invalid UTF-8 or a
 1511: bad configuration entry are reported with C<warn> (through L<Carp>) and
 1512: processing continues.  Catch them with C<$SIG{__WARN__}> if you need to
 1513: act on them.
 1514: 
 1515: =back
 1516: 
 1517: =head1 DESIGN NOTES
 1518: 
 1519: Some checks are made once, where data enters, and relied on afterwards.
 1520: Each rule below is proved by F<t/logic.t>.
 1521: 
 1522: =over 4
 1523: 
 1524: =item * B<Versions.>  Every version is checked when it is read (from the
 1525: F<Makefile.PL>, the existing F<cpanfile> or the configuration file) and
 1526: replaced by C<0> if it is not a version number or version range.  A
 1527: version number is zero exactly when none of its digits is 1 to 9, and a
 1528: range means "any version" only when it is C<E<gt>=> a zero version.  So,
 1529: when the output is written, those two tests decide whether to print a
 1530: requirement.
 1531: 
 1532: =item * B<Comments.>  An empty comment is stored as "no comment" when it
 1533: is read, and entries from other sources have no comment.  So, when the
 1534: output is written, a comment that exists is never empty and can be
 1535: printed without further checks.
 1536: 
 1537: =item * B<Developer tools.>  A tool must not be added if the develop
 1538: phase already lists it under any relationship.  So the set of listed
 1539: modules is built once, and every configured tool outside that set is
 1540: added.
 1541: 
 1542: =item * B<Speed.>  Parsing takes time proportional to the size of the
 1543: F<Makefile.PL>, however its blocks are arranged: every position test
 1544: (is this block inside a comment, or inside a C<prereqs> block?) is a
 1545: binary search over sorted, non-overlapping ranges.  Lines without a
 1546: C<#> skip the comment checks, the four simple keys are found in one
 1547: pass, and the patterns used on every line are compiled once.
 1548: 
 1549: =item * B<Order of checks.>  Each function stops at the first check that
 1550: fails: an unreadable F<Makefile.PL> is refused before anything is read,
 1551: and the configuration file is only parsed once it is known to exist and
 1552: to be a regular file.
 1553: 
 1554: =back
 1555: 
 1556: =head1 LIMITATIONS
 1557: 
 1558: =over 4
 1559: 
 1560: =item * The F<Makefile.PL> is read with patterns, not run, so dependencies
 1561: that are computed by code cannot be found (see L</COMMON PITFALLS>).
 1562: 
 1563: =item * Dependency lists nested more than four braces deep inside a
 1564: single entry are not fully read.  Normal F<Makefile.PL> files never
 1565: come close to this.
 1566: 
 1567: =item * Only one C<on 'develop'> section of an existing F<cpanfile> is
 1568: used: the first one.
 1569: 
 1570: =back
