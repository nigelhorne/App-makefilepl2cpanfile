  257: =head1 DESCRIPTION
  258: 
  259: A Perl distribution lists the modules it needs in its F<Makefile.PL>.
  260: Many tools (for example C<cpanm --installdeps .> and CI systems) prefer
  261: a F<cpanfile> instead.  This module reads a F<Makefile.PL> and writes the
  262: same list in F<cpanfile> form, so you only keep the list in one place.
  263: 
  264: The F<Makefile.PL> is B<never run>.  It is read as plain text and
  265: searched for the parts that list dependencies.  This makes the tool safe
  266: to use on code you do not trust, but it also means that it cannot see
  267: dependencies that are computed while the program runs (see
  268: L</COMMON PITFALLS>).
  269: 
  270: Reading takes time in proportion to the size of the input, however it is
  271: written, so a hostile F<Makefile.PL> or F<cpanfile> (for example one with
  272: thousands of unclosed braces) cannot make the tool hang.
  273: 
  274: =head2 What it reads
  275: 
  276: =over 4
  277: 
  278: =item * C<PREREQ_PM>, C<BUILD_REQUIRES>, C<TEST_REQUIRES> and
  279: C<CONFIGURE_REQUIRES>.  These become C<requires> lines in the C<runtime>,
  280: C<build>, C<test> and C<configure> phases.
  281: 
  282: =item * C<prereqs =E<gt> { PHASE =E<gt> { RELATIONSHIP =E<gt> { ... } } }>
  283: blocks (the CPAN::Meta::Spec version 2 layout), wherever they appear -
  284: also inside C<META_MERGE>.
  285: 
  286: =item * The older version 1 layout, directly inside C<META_MERGE>:
  287: C<requires>, C<recommends>, C<suggests> and C<conflicts> become lines of
  288: that kind in the C<runtime> phase; C<build_requires> and
  289: C<configure_requires> become C<requires> lines in the C<build> and
  290: C<configure> phases.
  291: 
  292: =item * C<MIN_PERL_VERSION>, which becomes C<requires 'perl', 'VERSION';>.
  293: 
  294: =item * A C<#> comment after an entry.  It is copied to the F<cpanfile>.
  295: 
  296: =back

  298: =head2 What it writes
  299: 
  300: 	# Generated from Makefile.PL using makefilepl2cpanfile
  301: 
  302: 	requires 'perl', '5.010';

  304: 	requires 'Moo', '2.000';   # object system
  305: 	requires 'Try::Tiny';
  306: 	recommends 'JSON::MaybeXS';

  308: 	on 'test' => sub {
  309: 		requires 'Test::More', '0.98';
  310: 	};
  311: 
  312: 	on 'develop' => sub {
  313: 		requires 'Perl::Critic';
  314: 	};

  316: Runtime dependencies come first, without an C<on> block.  The other
  317: phases follow in this order: C<configure>, C<build>, C<test>, C<develop>.
  318: Inside each phase, C<requires> lines come first, then C<recommends>, then
  319: C<suggests>, and the modules are in alphabetical order.  The same input
  320: always gives exactly the same output.

  322: =head1 CONFIGURATION
  323: 
  324: When C<with_develop> is true (the default), some developer tools are
  325: added to the C<develop> phase.  By default these are L<Devel::Cover>,
  326: L<Perl::Critic>, L<Test::Pod> and L<Test::Pod::Coverage>.
  327: 
  328: To choose your own list, create the file
  329: F<~/.config/makefilepl2cpanfile.yml>:
  330: 
  331: 	develop:
  332: 	  Perl::Critic: 0
  333: 	  Devel::Cover: 0
  334: 	  My::Extra::Tool: '1.00'
  335: 
  336: The number after each name is the minimum version; C<0> means "any
  337: version".  Your list B<replaces> the default list; it is not added to it.
  338: Names that are not valid module names, and versions that are not version
  339: numbers, are ignored with a warning, so a mistake in this file can never
  340: put unexpected code into your F<cpanfile>.

  342: =head1 DATA STRUCTURE
  343: 
  344: C<parse_prereqs()> returns a hash reference with three levels:
  345: 
  346: 	{
  347: 		PHASE => {
  348: 			RELATIONSHIP => {
  349: 				'Module::Name' => { version => '1.0', comment => 'why it is needed' },
  350: 			},
  351: 		},
  352: 	}
  353: 
  354: =over 4
  355: 
  356: =item * PHASE is one of C<runtime>, C<configure>, C<build>, C<test> or
  357: C<develop>.
  358: 
  359: =item * RELATIONSHIP is one of C<requires>, C<recommends>, C<suggests> or
  360: C<conflicts>.
  361: 
  362: =item * C<version> is the version requirement exactly as it was written:
  363: a single version (C<'1.60'> stays C<'1.60'>) or a version range such as
  364: C<'E<gt>= 1.2, E<lt> 2.0'>.  It is C<0> when there is no requirement.
  365: 
  366: =item * C<comment> is the text of the C<#> comment after the entry, or
  367: C<undef> when there is none.
  368: 
  369: =back
  370: 
  371: A phase or relationship with no modules is not present at all.

  373: =head1 ENCODING
  374: 
  375: =over 4
  376: 
  377: =item * B<The Makefile.PL file> is read as UTF-8.  Comments may contain
  378: any printable Unicode text, including accented letters, emoji and
  379: combining marks; they are copied to the output unchanged.  Control
  380: characters (other than TAB) and Unicode direction-override characters
  381: are removed from comments, so that the generated file cannot be made to
  382: look different from what it really contains.  If the file is not valid UTF-8 you get a
  383: warning and processing continues (see L</generate(%args)>).
  384: 
  385: =item * B<The returned cpanfile text> is a Perl character string.  Write
  386: it with a UTF-8 output layer, for example C<path(...)-E<gt>spew_utf8> or
  387: C<binmode $fh, ':encoding(UTF-8)'>.  Otherwise Perl warns
  388: "Wide character in print" when a comment contains non-ASCII text.
  389: 
  390: =item * B<The existing argument> and B<the content argument of
  391: parse_prereqs()> must be character strings: decode them first (for
  392: example with C<slurp_utf8>).  Raw bytes work for plain ASCII, but a
  393: non-ASCII comment would come back as separate bytes.
  394: 
  395: =item * B<Module names> must be plain ASCII (A-Z, a-z, 0-9, C<_> and
  396: C<::>), as CPAN requires.  A name with any other character is ignored.
  397: This also stops look-alike names, such as C<Test::More> written with a
  398: Cyrillic letter.
  399: 
  400: =item * B<Version numbers> may use only the ASCII digits 0-9, C<.>,
  401: C<_> and a leading C<v>, and must contain at least one digit.  A version
  402: range joins such numbers, each after one of the operators C<E<gt>=>,
  403: C<E<lt>=>, C<==>, C<!=>, C<E<gt>> or C<E<lt>>, with commas.  The whole
  404: value is checked: C<'1.0-TRIAL'> is not shortened to C<'1.0'>.  Anything
  405: else is treated as "no minimum version".
  406: 
  407: =item * B<The YAML configuration file> is read as UTF-8; the same rules
  408: for names and versions apply.
  409: 
  410: =item * B<File names> are passed to the operating system unchanged.
  411: Names with spaces, non-ASCII letters or shell characters such as C<;>
  412: and C<|> are safe: no shell is ever used.
  413: 
  414: =back

  418: =head2 generate(%args)
  419: 
  420: =head3 PURPOSE
  421: 
  422: Reads a F<Makefile.PL> and returns the text of a matching F<cpanfile>.
  423: The F<Makefile.PL> is read as text and is never run.
  424: 
  425: =head3 ARGUMENTS
  426: 
  427: Give the arguments as a list of name/value pairs, or as one hash
  428: reference.  All of them are optional.
  429: 
  430: =over 4
  431: 
  432: =item * C<content> - the text of a F<Makefile.PL>, for example from
  433: L</read_makefile($path)>.  When it is given it is used as it is, and
  434: C<makefile> is ignored and nothing is read.  Use it to read the file once
  435: and use the same text for more than one purpose.
  436: 
  437: =item * C<makefile> - the path of the F<Makefile.PL> to read.  Default:
  438: C<'Makefile.PL'> in the current directory.  Anything that turns into a
  439: path when used as a string is accepted, such as a L<Path::Tiny> object.
  440: A filehandle or another kind of reference is refused with
  441: C<Cannot read>.
  442: 
  443: =item * C<existing> - the text of your current F<cpanfile>.  Default:
  444: C<''> (none).  Only its C<on 'develop' =E<gt> sub { ... }> section is
  445: used.  Every C<requires>, C<recommends>, C<suggests> and C<conflicts>
  446: line in that section is copied to the new text, so your hand-written developer
  447: dependencies are kept.  Lines that are commented out are not copied.
  448: An entry whose name is not a valid module name is dropped.  An entry
  449: whose version is not a version number or version range is kept without a
  450: version, and you get a warning.
  451: 
  452: =item * C<with_develop> - true or false.  Default: true.  When true, the
  453: developer tools from the configuration file (see L</CONFIGURATION>), or
  454: the default tools, are added to the C<develop> phase as C<requires>.  A
  455: tool that is already in the develop phase, from the F<Makefile.PL> or
  456: from C<existing>, is left exactly as it is.
  457: 
  458: =back
  459: 
  460: =head3 RETURNS
  461: 
  462: A string: the complete F<cpanfile>.  It always starts with the line
  463: C<# Generated from Makefile.PL using makefilepl2cpanfile> and always ends
  464: with exactly one newline.  The layout is described in
  465: L</What it writes>.  A F<Makefile.PL> with no dependencies gives just
  466: the first line.
  467: 
  468: =head3 SIDE EFFECTS
  469: 
  470: =over 4
  471: 
  472: =item * Reads the C<makefile> file.
  473: 
  474: =item * When C<with_develop> is true, reads
  475: F<~/.config/makefilepl2cpanfile.yml> if it exists.
  476: 
  477: =item * Never writes, creates or deletes any file.
  478: 
  479: =item * May print warnings (see MESSAGES below).
  480: 
  481: =item * Does not change the caller's C<$@>, C<$!> or C<$_>.
  482: 
  483: =back

 1494: =head1 COMMON PITFALLS
 1495: 
 1496: =over 4
 1497: 
 1498: =item * B<Code in Makefile.PL is not run.>  Dependencies that are built
 1499: by code are not seen, for example C<PREREQ_PM =E<gt> \%deps> or a list
 1500: returned by a function.  Entries inside a condition, such as
 1501: C<$^O eq 'MSWin32' ? ('Win32' =E<gt> 0) : ()>, are seen but become
 1502: unconditional.  Write such dependencies as plain entries, or add them to
 1503: the F<cpanfile> another way.
 1504: 
 1505: =item * B<Only the develop section of an existing cpanfile is kept.>
 1506: Hand edits anywhere else (for example a C<feature> block or an extra
 1507: C<on 'test'> line) are lost when you regenerate.  Put hand-written
 1508: entries in C<on 'develop' =E<gt> sub { ... }>.
 1509: 
 1510: =item * B<Conditions inside the kept develop section are removed.>  An
 1511: C<if (...) { requires 'X' }> inside the develop block is carried over as
 1512: a plain C<requires 'X'>.  Comments in the develop block are not kept.
 1513: 
 1514: =item * B<Which entry wins.>  When the same module is listed twice in the
 1515: same phase and relationship, the first one wins.  The simple keys
 1516: (C<PREREQ_PM> and friends) are read before C<prereqs> blocks, and entries
 1517: from F<Makefile.PL> win over entries in the existing develop section.
 1518: The same module under two different relationships (for example
 1519: C<requires> and C<recommends>) is kept twice.
 1520: 
 1521: =item * B<The configuration file replaces the default tools.>  If you
 1522: list only C<My::Tool>, then C<Perl::Critic> and the others are no longer
 1523: added.  List them too if you want them.
 1524: 
 1525: =item * B<undef means "use the default".>  C<makefile =E<gt> undef> reads
 1526: F<Makefile.PL>; C<existing =E<gt> undef> is the same as C<''>; and
 1527: C<with_develop =E<gt> undef> means B<true>.  Use C<with_develop =E<gt> 0>
 1528: to turn developer tools off.
 1529: 
 1530: =item * B<parse_prereqs(undef) is silent.>  It returns an empty hash
 1531: reference with no warning, so a failed file read can look like "no
 1532: dependencies".  Check that the read worked before you call it.
 1533: 
 1534: =item * B<The output depends on who runs it.>  With C<with_develop> on,
 1535: the tool list comes from the home directory of the current user.  Use
 1536: C<with_develop =E<gt> 0> when every computer must produce the same file.
 1537: 
 1538: =item * B<generate() does not write any file.>  It returns the text.
 1539: Save it yourself (see L</SYNOPSIS>) or use the command-line tool.
 1540: 
 1541: =item * B<Relative paths> in C<makefile> are relative to the current
 1542: working directory, not to your script.
 1543: 
 1544: =item * B<Warnings are not errors.>  Problems such as invalid UTF-8 or a
 1545: bad configuration entry are reported with C<warn> (through L<Carp>) and
 1546: processing continues.  Catch them with C<$SIG{__WARN__}> if you need to
 1547: act on them.
 1548: 
 1549: =back

 1551: =head1 DESIGN NOTES
 1552: 
 1553: Some checks are made once, where data enters, and relied on afterwards.
 1554: Each rule below is proved by F<t/logic.t>.
 1555: 
 1556: =over 4
 1557: 
 1558: =item * B<Versions.>  Every version is checked when it is read (from the
 1559: F<Makefile.PL>, the existing F<cpanfile> or the configuration file) and
 1560: replaced by C<0> if it is not a version number or version range.  A
 1561: version number is zero exactly when none of its digits is 1 to 9, and a
 1562: range means "any version" only when it is C<E<gt>=> a zero version.  So,
 1563: when the output is written, those two tests decide whether to print a
 1564: requirement.
 1565: 
 1566: =item * B<Comments.>  An empty comment is stored as "no comment" when it
 1567: is read, and entries from other sources have no comment.  So, when the
 1568: output is written, a comment that exists is never empty and can be
 1569: printed without further checks.
 1570: 
 1571: =item * B<Developer tools.>  A tool must not be added if the develop
 1572: phase already lists it under any relationship.  So the set of listed
 1573: modules is built once, and every configured tool outside that set is
 1574: added.
 1575: 
 1576: =item * B<Speed.>  Parsing takes time proportional to the size of the
 1577: F<Makefile.PL>, however its blocks are arranged: every position test
 1578: (is this block inside a comment, or inside a C<prereqs> block?) is a
 1579: binary search over sorted, non-overlapping ranges.  Lines without a
 1580: C<#> skip the comment checks, the four simple keys are found in one
 1581: pass, and the patterns used on every line are compiled once.
 1582: 
 1583: =item * B<Order of checks.>  Each function stops at the first check that
 1584: fails: an unreadable F<Makefile.PL> is refused before anything is read,
 1585: and the configuration file is only parsed once it is known to exist and
 1586: to be a regular file.
 1587: 
 1588: =back

 1590: =head1 LIMITATIONS
 1591: 
 1592: =over 4
 1593: 
 1594: =item * The F<Makefile.PL> is read with patterns, not run, so dependencies
 1595: that are computed by code cannot be found (see L</COMMON PITFALLS>).
 1596: 
 1597: =item * Braces are matched without regard to quotes or comments, so an
 1598: unmatched C<{> or C<}> inside a string or a C<#> comment within a
 1599: dependency list can hide some or all of that list's entries.  Dependency
 1600: lists may otherwise nest to any depth.
 1601: 
 1602: =item * Only one C<on 'develop'> section of an existing F<cpanfile> is
 1603: used: the first one.
