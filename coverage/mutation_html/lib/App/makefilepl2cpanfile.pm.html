  217: =head1 DESCRIPTION
  218: 
  219: A Perl distribution lists the modules it needs in its F<Makefile.PL>.
  220: Many tools (for example C<cpanm --installdeps .> and CI systems) prefer
  221: a F<cpanfile> instead.  This module reads a F<Makefile.PL> and writes the
  222: same list in F<cpanfile> form, so you only keep the list in one place.
  223: 
  224: The F<Makefile.PL> is B<never run>.  It is read as plain text and
  225: searched for the parts that list dependencies.  This makes the tool safe
  226: to use on code you do not trust, but it also means that it cannot see
  227: dependencies that are computed while the program runs (see
  228: L</COMMON PITFALLS>).
  229: 
  230: =head2 What it reads
  231: 
  232: =over 4
  233: 
  234: =item * C<PREREQ_PM>, C<BUILD_REQUIRES>, C<TEST_REQUIRES> and
  235: C<CONFIGURE_REQUIRES>.  These become C<requires> lines in the C<runtime>,
  236: C<build>, C<test> and C<configure> phases.
  237: 
  238: =item * C<prereqs =E<gt> { PHASE =E<gt> { RELATIONSHIP =E<gt> { ... } } }>
  239: blocks (the CPAN::Meta::Spec version 2 layout), wherever they appear -
  240: also inside C<META_MERGE>.
  241: 
  242: =item * C<recommends =E<gt> { ... }> and C<suggests =E<gt> { ... }>
  243: directly inside C<META_MERGE> (the older version 1 layout).  These become
  244: C<recommends> and C<suggests> lines in the C<runtime> phase.
  245: 
  246: =item * C<MIN_PERL_VERSION>, which becomes C<requires 'perl', 'VERSION';>.
  247: 
  248: =item * A C<#> comment after an entry.  It is copied to the F<cpanfile>.
  249: 
  250: =back
  251: 
  252: =head2 What it writes
  253: 
  254: 	# Generated from Makefile.PL using makefilepl2cpanfile
  255: 
  256: 	requires 'perl', '5.010';
  257: 
  258: 	requires 'Moo', '2.000';   # object system
  259: 	requires 'Try::Tiny';
  260: 	recommends 'JSON::MaybeXS';
  261: 
  262: 	on 'test' => sub {
  263: 		requires 'Test::More', '0.98';
  264: 	};
  265: 
  266: 	on 'develop' => sub {
  267: 		requires 'Perl::Critic';
  268: 	};
  269: 
  270: Runtime dependencies come first, without an C<on> block.  The other
  271: phases follow in this order: C<configure>, C<build>, C<test>, C<develop>.
  272: Inside each phase, C<requires> lines come first, then C<recommends>, then
  273: C<suggests>, and the modules are in alphabetical order.  The same input
  274: always gives exactly the same output.
  275: 
  276: =head1 CONFIGURATION
  277: 
  278: When C<with_develop> is true (the default), some developer tools are
  279: added to the C<develop> phase.  By default these are L<Devel::Cover>,
  280: L<Perl::Critic>, L<Test::Pod> and L<Test::Pod::Coverage>.
  281: 
  282: To choose your own list, create the file
  283: F<~/.config/makefilepl2cpanfile.yml>:
  284: 
  285: 	develop:
  286: 	  Perl::Critic: 0
  287: 	  Devel::Cover: 0
  288: 	  My::Extra::Tool: '1.00'
  289: 
  290: The number after each name is the minimum version; C<0> means "any
  291: version".  Your list B<replaces> the default list; it is not added to it.
  292: Names that are not valid module names, and versions that are not version
  293: numbers, are ignored with a warning, so a mistake in this file can never
  294: put unexpected code into your F<cpanfile>.

  296: =head1 DATA STRUCTURE
  297: 
  298: C<parse_prereqs()> returns a hash reference with three levels:
  299: 
  300: 	{
  301: 		PHASE => {
  302: 			RELATIONSHIP => {
  303: 				'Module::Name' => { version => '1.0', comment => 'why it is needed' },
  304: 			},
  305: 		},
  306: 	}
  307: 
  308: =over 4
  309: 
  310: =item * PHASE is one of C<runtime>, C<configure>, C<build>, C<test> or
  311: C<develop>.
  312: 
  313: =item * RELATIONSHIP is one of C<requires>, C<recommends> or C<suggests>.
  314: 
  315: =item * C<version> is the minimum version exactly as it was written (for
  316: example C<'1.60'> stays C<'1.60'>).  It is C<0> when there is no minimum.
  317: 
  318: =item * C<comment> is the text of the C<#> comment after the entry, or
  319: C<undef> when there is none.
  320: 
  321: =back
  322: 
  323: A phase or relationship with no modules is not present at all.

  325: =head1 ENCODING
  326: 
  327: =over 4
  328: 
  329: =item * B<The Makefile.PL file> is read as UTF-8.  Comments may contain
  330: any printable Unicode text, including accented letters, emoji and
  331: combining marks; they are copied to the output unchanged.  Control
  332: characters (other than TAB) and Unicode direction-override characters
  333: are removed from comments, so that the generated file cannot be made to
  334: look different from what it really contains.  If the file is not valid UTF-8 you get a
  335: warning and processing continues (see L</generate(%args)>).
  336: 
  337: =item * B<The returned cpanfile text> is a Perl character string.  Write
  338: it with a UTF-8 output layer, for example C<path(...)-E<gt>spew_utf8> or
  339: C<binmode $fh, ':encoding(UTF-8)'>.  Otherwise Perl warns
  340: "Wide character in print" when a comment contains non-ASCII text.
  341: 
  342: =item * B<The existing argument> and B<the content argument of
  343: parse_prereqs()> must be character strings: decode them first (for
  344: example with C<slurp_utf8>).  Raw bytes work for plain ASCII, but a
  345: non-ASCII comment would come back as separate bytes.
  346: 
  347: =item * B<Module names> must be plain ASCII (A-Z, a-z, 0-9, C<_> and
  348: C<::>), as CPAN requires.  A name with any other character is ignored.
  349: This also stops look-alike names, such as C<Test::More> written with a
  350: Cyrillic letter.
  351: 
  352: =item * B<Version numbers> may use only the ASCII digits 0-9, C<.>,
  353: C<_> and a leading C<v>, and must contain at least one digit.  The whole
  354: value is checked: C<'1.0-TRIAL'> is not shortened to C<'1.0'>.  Anything
  355: else is treated as "no minimum version".
  356: 
  357: =item * B<The YAML configuration file> is read as UTF-8; the same rules
  358: for names and versions apply.
  359: 
  360: =item * B<File names> are passed to the operating system unchanged.
  361: Names with spaces, non-ASCII letters or shell characters such as C<;>
  362: and C<|> are safe: no shell is ever used.
  363: 
  364: =back

  366: =head1 METHODS

  368: =head2 generate(%args)
  369: 
  370: =head3 PURPOSE
  371: 
  372: Reads a F<Makefile.PL> and returns the text of a matching F<cpanfile>.
  373: The F<Makefile.PL> is read as text and is never run.
  374: 
  375: =head3 ARGUMENTS
  376: 
  377: Give the arguments as a list of name/value pairs, or as one hash
  378: reference.  All of them are optional.
  379: 
  380: =over 4
  381: 
  382: =item * C<makefile> - the path of the F<Makefile.PL> to read.  Default:
  383: C<'Makefile.PL'> in the current directory.  Anything that turns into a
  384: path when used as a string is accepted, such as a L<Path::Tiny> object.
  385: A filehandle or another kind of reference is refused with
  386: C<Cannot read>.
  387: 
  388: =item * C<existing> - the text of your current F<cpanfile>.  Default:
  389: C<''> (none).  Only its C<on 'develop' =E<gt> sub { ... }> section is
  390: used.  Every C<requires>, C<recommends> and C<suggests> line in that
  391: section is copied to the new text, so your hand-written developer
  392: dependencies are kept.  Lines that are commented out are not copied.
  393: An entry whose name is not a valid module name is dropped.  An entry
  394: whose version is not a version number is kept without a version, and
  395: you get a warning.
  396: 
  397: =item * C<with_develop> - true or false.  Default: true.  When true, the
  398: developer tools from the configuration file (see L</CONFIGURATION>), or
  399: the default tools, are added to the C<develop> phase as C<requires>.  A
  400: tool that is already in the develop phase, from the F<Makefile.PL> or
  401: from C<existing>, is left exactly as it is.
  402: 
  403: =back
  404: 
  405: =head3 RETURNS
  406: 
  407: A string: the complete F<cpanfile>.  It always starts with the line
  408: C<# Generated from Makefile.PL using makefilepl2cpanfile> and always ends
  409: with exactly one newline.  The layout is described in
  410: L</What it writes>.  A F<Makefile.PL> with no dependencies gives just
  411: the first line.
  412: 
  413: =head3 SIDE EFFECTS
  414: 
  415: =over 4
  416: 
  417: =item * Reads the C<makefile> file.
  418: 
  419: =item * When C<with_develop> is true, reads
  420: F<~/.config/makefilepl2cpanfile.yml> if it exists.
  421: 
  422: =item * Never writes, creates or deletes any file.
  423: 
  424: =item * May print warnings (see MESSAGES below).
  425: 
  426: =item * Does not change the caller's C<$@>, C<$!> or C<$_>.
  427: 
  428: =back

  432: 	use App::makefilepl2cpanfile;

  443: =head3 HOW IT WORKS
  444: 
  445: =over 4
  446: 
  447: =item 1. Check that C<makefile> is a readable, regular file.
  448: 
  449: =item 2. Read it as UTF-8.  If that fails because of bad UTF-8, warn and
  450: read the raw bytes instead.  Any other read error is passed on.
  451: 
  452: =item 3. Find C<MIN_PERL_VERSION> and call L</parse_prereqs($content)>.
  453: 
  454: =item 4. Copy the develop entries from C<existing>, without replacing
  455: entries that came from the F<Makefile.PL>.
  456: 
  457: =item 5. If C<with_develop> is true, add each configured tool that is
  458: not already in the develop phase.
  459: 
  460: =item 6. Format and return the text.
  461: 
  462: =back

 1265: =head1 COMMON PITFALLS
 1266: 
 1267: =over 4
 1268: 
 1269: =item * B<Code in Makefile.PL is not run.>  Dependencies that are built
 1270: by code are not seen, for example C<PREREQ_PM =E<gt> \%deps> or a list
 1271: returned by a function.  Entries inside a condition, such as
 1272: C<$^O eq 'MSWin32' ? ('Win32' =E<gt> 0) : ()>, are seen but become
 1273: unconditional.  Write such dependencies as plain entries, or add them to
 1274: the F<cpanfile> another way.
 1275: 
 1276: =item * B<Only the develop section of an existing cpanfile is kept.>
 1277: Hand edits anywhere else (for example a C<feature> block or an extra
 1278: C<on 'test'> line) are lost when you regenerate.  Put hand-written
 1279: entries in C<on 'develop' =E<gt> sub { ... }>.
 1280: 
 1281: =item * B<Conditions inside the kept develop section are removed.>  An
 1282: C<if (...) { requires 'X' }> inside the develop block is carried over as
 1283: a plain C<requires 'X'>.  Comments in the develop block are not kept.
 1284: 
 1285: =item * B<Which entry wins.>  When the same module is listed twice in the
 1286: same phase and relationship, the first one wins.  The simple keys
 1287: (C<PREREQ_PM> and friends) are read before C<prereqs> blocks, and entries
 1288: from F<Makefile.PL> win over entries in the existing develop section.
 1289: The same module under two different relationships (for example
 1290: C<requires> and C<recommends>) is kept twice.
 1291: 
 1292: =item * B<The configuration file replaces the default tools.>  If you
 1293: list only C<My::Tool>, then C<Perl::Critic> and the others are no longer
 1294: added.  List them too if you want them.
 1295: 
 1296: =item * B<undef means "use the default".>  C<makefile =E<gt> undef> reads
 1297: F<Makefile.PL>; C<existing =E<gt> undef> is the same as C<''>; and
 1298: C<with_develop =E<gt> undef> means B<true>.  Use C<with_develop =E<gt> 0>
 1299: to turn developer tools off.
 1300: 
 1301: =item * B<parse_prereqs(undef) is silent.>  It returns an empty hash
 1302: reference with no warning, so a failed file read can look like "no
 1303: dependencies".  Check that the read worked before you call it.
 1304: 
 1305: =item * B<The output depends on who runs it.>  With C<with_develop> on,
 1306: the tool list comes from the home directory of the current user.  Use
 1307: C<with_develop =E<gt> 0> when every computer must produce the same file.

 1322: =head1 DESIGN NOTES
 1323: 
 1324: Some checks are made once, where data enters, and relied on afterwards.
 1325: Each rule below is proved by F<t/logic.t>.
 1326: 
 1327: =over 4
 1328: 
 1329: =item * B<Versions.>  Every version is checked when it is read (from the
 1330: F<Makefile.PL>, the existing F<cpanfile> or the configuration file) and
 1331: replaced by C<0> if it is not a version number.  A version number is
 1332: zero exactly when none of its digits is 1 to 9.  So, when the output is
 1333: written, "does it contain a digit from 1 to 9?" is the whole test for
 1334: whether to print a minimum version.
 1335: 
 1336: =item * B<Comments.>  An empty comment is stored as "no comment" when it
 1337: is read, and entries from other sources have no comment.  So, when the
 1338: output is written, a comment that exists is never empty and can be
 1339: printed without further checks.
 1340: 
 1341: =item * B<Developer tools.>  A tool must not be added if the develop
 1342: phase already lists it under any relationship.  So the set of listed
 1343: modules is built once, and every configured tool outside that set is
 1344: added.
 1345: 
 1346: =item * B<Speed.>  Parsing takes time proportional to the size of the
 1347: F<Makefile.PL>, however its blocks are arranged: every position test
 1348: (is this block inside a comment, or inside a C<prereqs> block?) is a
 1349: binary search over sorted, non-overlapping ranges.  Lines without a
 1350: C<#> skip the comment checks, the four simple keys are found in one
 1351: pass, and the patterns used on every line are compiled once.
 1352: 
 1353: =item * B<Order of checks.>  Each function stops at the first check that
 1354: fails: an unreadable F<Makefile.PL> is refused before anything is read,
 1355: and the configuration file is only parsed once it is known to exist and
 1356: to be a regular file.
 1357: 
 1358: =back
