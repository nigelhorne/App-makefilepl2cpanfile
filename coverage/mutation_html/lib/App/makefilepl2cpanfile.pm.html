  156: =head1 DESCRIPTION
  157: 
  158: A Perl distribution lists the modules it needs in its F<Makefile.PL>.
  159: Many tools (for example C<cpanm --installdeps .> and CI systems) prefer
  160: a F<cpanfile> instead.  This module reads a F<Makefile.PL> and writes the
  161: same list in F<cpanfile> form, so you only keep the list in one place.
  162: 
  163: The F<Makefile.PL> is B<never run>.  It is read as plain text and
  164: searched for the parts that list dependencies.  This makes the tool safe
  165: to use on code you do not trust, but it also means that it cannot see
  166: dependencies that are computed while the program runs (see
  167: L</COMMON PITFALLS>).
  168: 
  169: =head2 What it reads
  170: 
  171: =over 4
  172: 
  173: =item * C<PREREQ_PM>, C<BUILD_REQUIRES>, C<TEST_REQUIRES> and
  174: C<CONFIGURE_REQUIRES>.  These become C<requires> lines in the C<runtime>,
  175: C<build>, C<test> and C<configure> phases.
  176: 
  177: =item * C<prereqs =E<gt> { PHASE =E<gt> { RELATIONSHIP =E<gt> { ... } } }>
  178: blocks (the CPAN::Meta::Spec version 2 layout), wherever they appear -
  179: also inside C<META_MERGE>.
  180: 
  181: =item * C<recommends =E<gt> { ... }> and C<suggests =E<gt> { ... }>
  182: directly inside C<META_MERGE> (the older version 1 layout).  These become
  183: C<recommends> and C<suggests> lines in the C<runtime> phase.
  184: 
  185: =item * C<MIN_PERL_VERSION>, which becomes C<requires 'perl', 'VERSION';>.
  186: 
  187: =item * A C<#> comment after an entry.  It is copied to the F<cpanfile>.
  188: 
  189: =back
  190: 
  191: =head2 What it writes
  192: 
  193: 	# Generated from Makefile.PL using makefilepl2cpanfile
  194: 
  195: 	requires 'perl', '5.010';

  197: 	requires 'Moo', '2.000';   # object system
  198: 	requires 'Try::Tiny';
  199: 	recommends 'JSON::MaybeXS';
  200: 
  201: 	on 'test' => sub {
  202: 		requires 'Test::More', '0.98';
  203: 	};
  204: 
  205: 	on 'develop' => sub {
  206: 		requires 'Perl::Critic';
  207: 	};
  208: 
  209: Runtime dependencies come first, without an C<on> block.  The other
  210: phases follow in this order: C<configure>, C<build>, C<test>, C<develop>.
  211: Inside each phase, C<requires> lines come first, then C<recommends>, then
  212: C<suggests>, and the modules are in alphabetical order.  The same input
  213: always gives exactly the same output.
  214: 
  215: =head1 CONFIGURATION
  216: 
  217: When C<with_develop> is true (the default), some developer tools are
  218: added to the C<develop> phase.  By default these are L<Devel::Cover>,
  219: L<Perl::Critic>, L<Test::Pod> and L<Test::Pod::Coverage>.
  220: 
  221: To choose your own list, create the file
  222: F<~/.config/makefilepl2cpanfile.yml>:
  223: 
  224: 	develop:
  225: 	  Perl::Critic: 0
  226: 	  Devel::Cover: 0
  227: 	  My::Extra::Tool: '1.00'
  228: 
  229: The number after each name is the minimum version; C<0> means "any
  230: version".  Your list B<replaces> the default list; it is not added to it.
  231: Names that are not valid module names, and versions that are not version
  232: numbers, are ignored with a warning, so a mistake in this file can never
  233: put unexpected code into your F<cpanfile>.

  235: =head1 DATA STRUCTURE
  236: 
  237: C<parse_prereqs()> returns a hash reference with three levels:
  238: 
  239: 	{
  240: 		PHASE => {
  241: 			RELATIONSHIP => {
  242: 				'Module::Name' => { version => '1.0', comment => 'why it is needed' },
  243: 			},
  244: 		},
  245: 	}
  246: 
  247: =over 4
  248: 
  249: =item * PHASE is one of C<runtime>, C<configure>, C<build>, C<test> or
  250: C<develop>.
  251: 
  252: =item * RELATIONSHIP is one of C<requires>, C<recommends> or C<suggests>.
  253: 
  254: =item * C<version> is the minimum version exactly as it was written (for
  255: example C<'1.60'> stays C<'1.60'>).  It is C<0> when there is no minimum.
  256: 
  257: =item * C<comment> is the text of the C<#> comment after the entry, or
  258: C<undef> when there is none.
  259: 
  260: =back
  261: 
  262: A phase or relationship with no modules is not present at all.

  264: =head1 ENCODING
  265: 
  266: =over 4
  267: 
  268: =item * B<The Makefile.PL file> is read as UTF-8.  Comments may contain
  269: any printable Unicode text, including accented letters, emoji and
  270: combining marks; they are copied to the output unchanged.  Control
  271: characters (other than TAB) and Unicode direction-override characters
  272: are removed from comments, so that the generated file cannot be made to
  273: look different from what it really contains.  If the file is not valid UTF-8 you get a
  274: warning and processing continues (see L</generate(%args)>).
  275: 
  276: =item * B<The returned cpanfile text> is a Perl character string.  Write
  277: it with a UTF-8 output layer, for example C<path(...)-E<gt>spew_utf8> or
  278: C<binmode $fh, ':encoding(UTF-8)'>.  Otherwise Perl warns
  279: "Wide character in print" when a comment contains non-ASCII text.
  280: 
  281: =item * B<The existing argument> and B<the content argument of
  282: parse_prereqs()> must be character strings: decode them first (for
  283: example with C<slurp_utf8>).  Raw bytes work for plain ASCII, but a
  284: non-ASCII comment would come back as separate bytes.
  285: 
  286: =item * B<Module names> must be plain ASCII (A-Z, a-z, 0-9, C<_> and
  287: C<::>), as CPAN requires.  A name with any other character is ignored.
  288: This also stops look-alike names, such as C<Test::More> written with a
  289: Cyrillic letter.
  290: 
  291: =item * B<Version numbers> may use only the ASCII digits 0-9, C<.>,
  292: C<_> and a leading C<v>, and must contain at least one digit.  The whole
  293: value is checked: C<'1.0-TRIAL'> is not shortened to C<'1.0'>.  Anything
  294: else is treated as "no minimum version".
  295: 
  296: =item * B<The YAML configuration file> is read as UTF-8; the same rules
  297: for names and versions apply.
  298: 
  299: =item * B<File names> are passed to the operating system unchanged.
  300: Names with spaces, non-ASCII letters or shell characters such as C<;>
  301: and C<|> are safe: no shell is ever used.
  302: 
  303: =back

  307: =head2 generate(%args)
  308: 
  309: =head3 PURPOSE
  310: 
  311: Reads a F<Makefile.PL> and returns the text of a matching F<cpanfile>.
  312: The F<Makefile.PL> is read as text and is never run.
  313: 
  314: =head3 ARGUMENTS
  315: 
  316: Give the arguments as a list of name/value pairs, or as one hash
  317: reference.  All of them are optional.
  318: 
  319: =over 4
  320: 
  321: =item * C<makefile> - the path of the F<Makefile.PL> to read.  Default:
  322: C<'Makefile.PL'> in the current directory.  Anything that turns into a
  323: path when used as a string is accepted, such as a L<Path::Tiny> object.
  324: A filehandle or another kind of reference is refused with
  325: C<Cannot read>.
  326: 
  327: =item * C<existing> - the text of your current F<cpanfile>.  Default:
  328: C<''> (none).  Only its C<on 'develop' =E<gt> sub { ... }> section is
  329: used.  Every C<requires>, C<recommends> and C<suggests> line in that
  330: section is copied to the new text, so your hand-written developer
  331: dependencies are kept.  Lines that are commented out are not copied.
  332: An entry whose name is not a valid module name is dropped.  An entry
  333: whose version is not a version number is kept without a version, and
  334: you get a warning.
  335: 
  336: =item * C<with_develop> - true or false.  Default: true.  When true, the
  337: developer tools from the configuration file (see L</CONFIGURATION>), or
  338: the default tools, are added to the C<develop> phase as C<requires>.  A
  339: tool that is already in the develop phase, from the F<Makefile.PL> or
  340: from C<existing>, is left exactly as it is.
  341: 
  342: =back
  343: 
  344: =head3 RETURNS
  345: 
  346: A string: the complete F<cpanfile>.  It always starts with the line
  347: C<# Generated from Makefile.PL using makefilepl2cpanfile> and always ends
  348: with exactly one newline.  The layout is described in
  349: L</What it writes>.  A F<Makefile.PL> with no dependencies gives just
  350: the first line.
  351: 
  352: =head3 SIDE EFFECTS
  353: 
  354: =over 4
  355: 
  356: =item * Reads the C<makefile> file.
  357: 
  358: =item * When C<with_develop> is true, reads
  359: F<~/.config/makefilepl2cpanfile.yml> if it exists.
  360: 
  361: =item * Never writes, creates or deletes any file.
  362: 
  363: =item * May print warnings (see MESSAGES below).
  364: 
  365: =item * Does not change the caller's C<$@>, C<$!> or C<$_>.
  366: 
  367: =back

  382: =head3 HOW IT WORKS
  383: 
  384: =over 4
  385: 
  386: =item 1. Check that C<makefile> is a readable, regular file.
  387: 
  388: =item 2. Read it as UTF-8.  If that fails because of bad UTF-8, warn and
  389: read the raw bytes instead.  Any other read error is passed on.
  390: 
  391: =item 3. Find C<MIN_PERL_VERSION> and call L</parse_prereqs($content)>.
  392: 
  393: =item 4. Copy the develop entries from C<existing>, without replacing
  394: entries that came from the F<Makefile.PL>.
  395: 
  396: =item 5. If C<with_develop> is true, add each configured tool that is
  397: not already in the develop phase.
  398: 
  399: =item 6. Format and return the text.
  400: 
  401: =back

 1174: =head1 COMMON PITFALLS
 1175: 
 1176: =over 4
 1177: 
 1178: =item * B<Code in Makefile.PL is not run.>  Dependencies that are built
 1179: by code are not seen, for example C<PREREQ_PM =E<gt> \%deps> or a list
 1180: returned by a function.  Entries inside a condition, such as
 1181: C<$^O eq 'MSWin32' ? ('Win32' =E<gt> 0) : ()>, are seen but become
 1182: unconditional.  Write such dependencies as plain entries, or add them to
 1183: the F<cpanfile> another way.
 1184: 
 1185: =item * B<Only the develop section of an existing cpanfile is kept.>
 1186: Hand edits anywhere else (for example a C<feature> block or an extra
 1187: C<on 'test'> line) are lost when you regenerate.  Put hand-written
 1188: entries in C<on 'develop' =E<gt> sub { ... }>.
 1189: 
 1190: =item * B<Conditions inside the kept develop section are removed.>  An
 1191: C<if (...) { requires 'X' }> inside the develop block is carried over as
 1192: a plain C<requires 'X'>.  Comments in the develop block are not kept.
 1193: 
 1194: =item * B<Which entry wins.>  When the same module is listed twice in the
 1195: same phase and relationship, the first one wins.  The simple keys
 1196: (C<PREREQ_PM> and friends) are read before C<prereqs> blocks, and entries
 1197: from F<Makefile.PL> win over entries in the existing develop section.
 1198: The same module under two different relationships (for example
 1199: C<requires> and C<recommends>) is kept twice.
 1200: 
 1201: =item * B<The configuration file replaces the default tools.>  If you
 1202: list only C<My::Tool>, then C<Perl::Critic> and the others are no longer
 1203: added.  List them too if you want them.
 1204: 
 1205: =item * B<undef means "use the default".>  C<makefile =E<gt> undef> reads
 1206: F<Makefile.PL>; C<existing =E<gt> undef> is the same as C<''>; and
 1207: C<with_develop =E<gt> undef> means B<true>.  Use C<with_develop =E<gt> 0>
 1208: to turn developer tools off.
 1209: 
 1210: =item * B<parse_prereqs(undef) is silent.>  It returns an empty hash
 1211: reference with no warning, so a failed file read can look like "no
 1212: dependencies".  Check that the read worked before you call it.
 1213: 
 1214: =item * B<The output depends on who runs it.>  With C<with_develop> on,
 1215: the tool list comes from the home directory of the current user.  Use
 1216: C<with_develop =E<gt> 0> when every computer must produce the same file.
 1217: 
 1218: =item * B<generate() does not write any file.>  It returns the text.
 1219: Save it yourself (see L</SYNOPSIS>) or use the command-line tool.
 1220: 
 1221: =item * B<Relative paths> in C<makefile> are relative to the current
 1222: working directory, not to your script.
 1223: 
 1224: =item * B<Warnings are not errors.>  Problems such as invalid UTF-8 or a
 1225: bad configuration entry are reported with C<warn> (through L<Carp>) and
 1226: processing continues.  Catch them with C<$SIG{__WARN__}> if you need to
 1227: act on them.
 1228: 
 1229: =back

 1231: =head1 DESIGN NOTES
 1232: 
 1233: Some checks are made once, where data enters, and relied on afterwards.
 1234: Each rule below is proved by F<t/logic.t>.
 1235: 
 1236: =over 4
 1237: 
 1238: =item * B<Versions.>  Every version is checked when it is read (from the
 1239: F<Makefile.PL>, the existing F<cpanfile> or the configuration file) and
 1240: replaced by C<0> if it is not a version number.  A version number is
 1241: zero exactly when none of its digits is 1 to 9.  So, when the output is
 1242: written, "does it contain a digit from 1 to 9?" is the whole test for
 1243: whether to print a minimum version.
 1244: 
 1245: =item * B<Comments.>  An empty comment is stored as "no comment" when it
 1246: is read, and entries from other sources have no comment.  So, when the
 1247: output is written, a comment that exists is never empty and can be
 1248: printed without further checks.
 1249: 
 1250: =item * B<Developer tools.>  A tool must not be added if the develop
 1251: phase already lists it under any relationship.  So the set of listed
 1252: modules is built once, and every configured tool outside that set is
 1253: added.
 1254: 
 1255: =item * B<Speed.>  Parsing takes time proportional to the size of the
 1256: F<Makefile.PL>, however its blocks are arranged: every position test
 1257: (is this block inside a comment, or inside a C<prereqs> block?) is a
 1258: binary search over sorted, non-overlapping ranges.  Lines without a
 1259: C<#> skip the comment checks, the four simple keys are found in one
 1260: pass, and the patterns used on every line are compiled once.
 1261: 
 1262: =item * B<Order of checks.>  Each function stops at the first check that
 1263: fails: an unreadable F<Makefile.PL> is refused before anything is read,
 1264: and the configuration file is only parsed once it is known to exist and
 1265: to be a regular file.
 1266: 
 1267: =back

 1269: =head1 LIMITATIONS
 1270: 
 1271: =over 4
 1272: 
 1273: =item * The F<Makefile.PL> is read with patterns, not run, so dependencies
 1274: that are computed by code cannot be found (see L</COMMON PITFALLS>).
 1275: 
 1276: =item * Dependency lists nested more than four braces deep inside a
 1277: single entry are not fully read.  Normal F<Makefile.PL> files never
 1278: come close to this.
 1279: 
 1280: =item * Only one C<on 'develop'> section of an existing F<cpanfile> is
 1281: used: the first one.
